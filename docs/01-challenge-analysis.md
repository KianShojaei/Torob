# تحلیل چالش «دستیار هوشمند خرید حضوری»

> **مسابقه:** استارکوچ / ترب — دستیار ایجنتیک خرید حضوری در تهران
> **نسخه:** ۱٫۰ — ۲۰۲۶/۱۰/۲۳
> **وضعیت:** تحلیل کامل بریف انجام شد. پروفایل دیتاست در انتظار دریافت فایل CSV است (هاست آروان از محیط توسعه در دسترس نیست).

---

## ۰. خلاصه در یک نگاه

آنچه ساخته می‌شود نباید «چت‌بات فروشگاه‌یاب» باشد. مسئله واقعی این است:

> **«آیا ارزش دارد برای این محصول، الان، به این مغازه بروم؟»**

دستیار باید کاربر را از لحظه‌ی «نمی‌دانم چه مدلی می‌خواهم» تا لحظه‌ی «جلوی در مغازه، با قیمت و موجودی تأییدشده» همراهی کند. این یعنی محصول باید چهار چیز را همزمان حل کند:

1. **کشف نیاز** (کدام محصول/مدل؟)
2. **انتخاب فروشنده** (کدام مغازه، با توجه به فاصله، قیمت، ساعت کاری و شرایط خرید؟)
3. **تأیید اطلاعات** (قیمت و موجودی ثبت‌شده قدیمی است؛ باید از فروشنده پرسید)
4. **اجرای سفر** (مسیر، آدرس دقیق داخل پاساژ، و جایگزین فوری اگر مغازه بسته بود)

سه لایه‌ی امتیازدهی (محصول ۷۵ + UX ۷۵ + هوشمندی ۵۰ = ۲۰۰ از ۳۰۰) دقیقاً روی همین چهار مورد متمرکز است؛ نه روی پیچیدگی فنی.

## ۱. صورت مسئله واقعی

### ۱.۱ تفاوت خرید حضوری با خرید آنلاین

در خرید آنلاین، «قیمت» و «موجودی» دو فیلد قطعی هستند. در خرید حضوری:

| عامل | ماهیت | ریسک برای کاربر |
|---|---|---|
| قیمت ثبت‌شده در ترب | **خوداظهاری فروشنده**، داده‌ی حدوداً یک هفته‌ای | سر صحنه گران‌تر می‌شود |
| موجودی | **اصلاً در دیتاست نیست** | می‌رود و پیدا نمی‌کند |
| ساعت کاری | ثبت‌شده ولی ممکن است استثنا داشته باشد | دم در بسته می‌بیند |
| شرایط اقساط | «اعلام‌شده» توسط فروشنده، نه تأییدشده | برنامه‌ی مالی به هم می‌ریزد |
| آدرس داخل پاساژ | متن آزاد، بدون نقشه‌ی داخلی | مغازه را پیدا نمی‌کند |
| پاسخ‌گویی فروشنده | نامشخص | وقت تلف می‌شود |

### ۱.۲ معادله‌ی «ارزش رفتن»

هر پیشنهاد فروشنده باید بر اساس یک هزینه‌ی کل انتظاری رتبه‌بندی شود، نه فقط قیمت:

```
هزینه کل انتظاری =
    قیمت محصول
  + هزینه/زمان سفر (فاصله)
  + ریسک تعطیل بودن (ساعت کاری × تأیید نبودن)
  + ریسک نبود موجودی (تأیید نشده بودن)
  − ارزش آفرها (اقساط، کالابرگ، ترب‌پی، هدیه)
```

این معادله باید **قابل تنظیم توسط کاربر** باشد (اسلایدر «برام قیمت مهم‌تره» / «نزدیکی مهم‌تره») و **قابل توضیح** («چرا این مغازه؟»). این دقیقاً همان چیزی است که داوران در بخش «محصول» و «UX» دنبالش هستند.

### ۱.۳ شش گام محصول (چهار گام رسمی + دو گام پنهان)

بریف چهار گام را نام برده است، اما تجربه‌ی واقعی دو گام دیگر هم دارد:

| گام | نام | خروجی قابل مشاهده |
|---|---|---|
| ۰ | **کشف نیاز** | کاربر می‌فهمد چه مدلی می‌خواهد |
| ۱ | **کوتاه‌سازی و مقایسه محصول** | ۳ تا ۵ گزینه با دلیل پیشنهاد |
| ۲ | **یافتن فروشنده‌های نزدیک** | لیست/نقشه مغازه‌های دارای آن محصول |
| ۳ | **مقایسه فروشنده‌ها** | قیمت، فاصله، ساعت کاری، اقساط، اعتبار داده |
| ۴ | **ارتباط و تأیید** | پیام به فروشنده، پاسخ، قیمت/موجودی تأییدشده |
| ۵ | **اجرای سفر** | مسیر، آدرس داخل پاساژ، جایگزین فوری |

گام‌های ۰ و ۵ همان «پین‌پوینت»هایی هستند که در بریف به آن‌ها اشاره شده و بیشترین تمایز محصولی را می‌سازند.

## ۲. تحلیل بند‌به‌بند بریف

| # | الزام بریف | ترجمه‌ی محصولی | ریسک اجرا |
|---|---|---|---|
| ۱ | کمک به انتخاب محصول وقتی کاربر مدل را نمی‌داند | گفت‌وگوی کوتاه + چیپ‌های نیاز + کارت‌های مقایسه + «چرا این؟» | پرسش‌های زیاد کاربر را فراری می‌دهد |
| ۲ | مقایسه محصولات و قیمت‌ها با توجه به معیارهای کاربر | صفحه‌ی مقایسه‌ی ۲-۴ محصول با تفاوت‌های مهم | مقایسه‌ی همه‌چیز = بی‌فایده |
| ۳ | پیشنهاد نهایی محصول/مدل | کارت تصمیم با گزینه‌ی اصلی + جایگزین ارزان/گران | عدم شفافیت در دلیل |
| ۴ | یافتن فروشگاه‌هایی که محصول را دارند | جست‌وجوی offer-based (نه category-based) + نقشه | اشتباه رایج: دسته‌بندی فعالیت ≠ موجود بودن محصول |
| ۵ | پیشنهاد مناطق و فروشگاه‌های نزدیک بر اساس لوکیشن | شعاع/محله/نقشه + مرتب‌سازی بر اساس فاصله | لوکیشن پیش‌فرض کاربر نامشخص است |
| ۶ | مقایسه فروشگاه‌ها از نظر قیمت، فاصله، ساعت کاری | جدول/کارت مقایسه + وضعیت «الان باز است» | ساعت کاری ممکن است برای همه ثبت نشده باشد |
| ۷ | ارتباط با فروشگاه و پرسش‌وپاسخ (ساعت کاری، قیمت، موجودی) | پیام ساختاریافته + صندوق فروشنده + پارس پاسخ | **شماره همه فروشگاه‌ها جعلی است** |
| ۸ | افزودن فیچر به سلیقه‌ی خود | بسته‌ی فیچرهای بخش ۶ | پراکندگی و نیمه‌کاره ماندن |
| ۹ | قیمت ثبت‌شده قدیمی است؛ استفاده از نتایج گوگل + تماس | لایه‌ی تأیید + نشان «تازگی» + جست‌وجوی وب | وابستگی به API خارجی و نرخ خطا |
| ۱۰ | وقتی فروشنده جواب نمی‌دهد یا مغازه بسته است، جایگزین سریع | تایم‌اوت + «مسابقه‌ی تأیید» + جایگزین‌های نزدیک | باید در دمو قابل نمایش باشد |
| ۱۱ | پیدا کردن مغازه داخل پاساژ از روی اطلاعات متنی | پارس آدرس (پاساژ/طبقه/واحد) + جمله‌ی پرسیدن از نگهبان | نقشه‌ی داخلی نداریم |
| ۱۲ | فیلتر خرید اقساطی | فیلتر + نشان منبع اطلاعات (اعلام‌شده/تأییدشده) | داده ممکن است فقط بولین باشد |
| ۱۳ | استفاده از دیتاست ترب | استفاده‌ی کامل از shops/products/offers + شفافیت | کیفیت داده پایین است |
| ۱۴ | دیپلوی (لیارا) | Docker + دیتابیس مدیریت‌شده + Healthcheck + CI | تحریم/دسترسی LLM از ایران |
| ۱۵ | UX فارسی، RTL و موبایل | طراحی mobile-first با فونت وزیرمتن | — |

## ۳. تحلیل دیتاست

### ۳.۱ جداول و معنای هرکدام

| جدول | سطح داده | نقش در محصول |
|---|---|---|
| `shops` | هر رکورد = یک کسب‌وکار | مکان، ساعت کاری، تماس، شرایط خرید، هویت |
| `products` | هر رکورد = یک محصول پایه (BaseProduct) | عنوان، برند، دسته، مشخصات، تصویر |
| `offers` | هر رکورد = یک آفر «فروشگاه × محصول» | قیمت، گارانتی، زمان آخرین تغییر قیمت |

نکته‌ی کلیدی: **`products` موجود بودن را نشان نمی‌دهد؛ `offers` نشان می‌دهد.** هر جا از دسته‌بندی فعالیت برای حدس موجود بودن استفاده کنیم، باید با برچسب «احتمالی» و جدا از نتایج قطعی نمایش داده شود.

### ۳.۲ اعداد کلیدی و یک هشدار مهم

متن PDF فارسی و راست‌به‌چپ است و در استخراج، برخی اعداد برعکس شده‌اند (`۵۷` در واقع `۷۵` است؛ جمع بارم‌بندی ۳۰۰ تأیید می‌کند). با در نظر گرفتن این موضوع:

| عدد | مقدار محتمل | توضیح |
|---|---|---|
| تعداد فروشگاه‌ها | **۶٬۴۷۶** | از جمع ۱۱۲ نام واقعی + ۶٬۳۶۴ نام جعلی |
| نام‌های جعلی | **۶٬۳۶۴** | ۹۸٪ فروشگاه‌ها |
| نام‌های واقعی | **۱۱۲** | ۹۰ اینستاگرام + ۲۲ وب‌سایت |
| سقف محصول هر فروشگاه | **۳۰۰** | — |
| سهم از فروشگاه‌های تهران | **۱۰٪** | انتخابی از مناطق خاص |
| محصولات یکتا | **۲۲۵٬۹۰۳ یا ۳۰۹٬۵۲۲** | ⚠️ نیاز به تأیید از CSV |
| تعداد آفرها | **۳۳۱٬۵۰۶ یا ۶۰۵٬۱۳۳** | ⚠️ نیاز به تأیید از CSV |
| تاریخ داده | حدود **یک هفته** قبل | مبنای محاسبه‌ی «تازگی» |

> این اعداد در سند نهایی و در دمو باید از خود CSV خوانده شوند؛ هیچ عددی را هاردکد نمی‌کنیم.

### ۳.۳ محدودیت‌های داده و اثرشان روی طراحی

| محدودیت | اثر مستقیم روی محصول |
|---|---|
| نام ۹۸٪ فروشگاه‌ها جعلی است | نمایش نام نباید تنها راه شناسایی باشد؛ محله، آدرس و دسته را برجسته کن |
| **تمام شماره‌ها جعلی‌اند** | تماس/پیام واقعی ممکن نیست → باید کانال «صندوق فروشنده» و شبیه‌سازی داشته باشیم |
| فقط ۱۱۲ فروشگاه هویت واقعی (اینستاگرام/سایت) دارند | مسیر «بررسی پیج اینستاگرام» فقط برای همان‌ها معنا دارد |
| لوکیشن واقعی است | نقشه و فاصله قابل اتکاست |
| فقط ۱۰٪ فروشگاه‌های تهران و مناطق انتخابی | **پوشش جغرافیایی ناقص است**؛ باید در UI شفاف باشد |
| سقف ۳۰۰ محصول برای هر فروشگاه | «همه‌ی محصولات این مغازه» وجود ندارد؛ نباید القا شود |
| موجودی در دیتاست نیست | باید از فروشنده پرسید؛ «موجود» فقط پس از تأیید |
| قیمت یک هفته‌ای | هر قیمت باید «عمر داده» داشته باشد |
| نوع اطلاعات اقساط (اعلام‌شده/تأییدشده) | فیلتر اقساط باید منبع را نشان دهد، نه فقط تیک |
| آدرس متنی شامل پاساژ/طبقه/واحد | فرصت ساخت «دستیار پاساژ» |

### ۳.۴ سلسله‌مراتب حقیقت (هسته‌ی شفافیت محصول)

این چهار سطح نباید هرگز با هم قاطی شوند:

| سطح | منبع | نمایش در UI |
|---|---|---|
| **L0 — ثبت‌شده** | ردیف `offers` | «قیمت ثبت‌شده در ترب» + «آخرین تغییر: ۶ روز پیش» |
| **L1 — استنتاج سیستم** | ساعت کاری، فاصله، دسته‌بندی | «الان باز است» (خاکستری/آبی) — نه «موجود است» |
| **L2 — تأیید فروشنده** | پاسخ صندوق فروشنده/کانال | «تأییدشده امروز ۱۴:۰۲ · واتساپ» |
| **L3 — تأیید کاربر** | گزارش پس از مراجعه | «کاربر دیروز خرید کرد» |

قاعده‌ی طلایی: **هیچ عددی در UI از LLM نمی‌آید.** قیمت، فاصله و زمان فقط از دیتابیس/tool می‌آیند و LLM فقط توضیح می‌دهد.

### ۳.۵ چیزهایی که دیتاست ندارد و باید طراحی کنیم

- موجودی لحظه‌ای و رزرو
- قیمت واقعی امروز
- نقشه‌ی داخلی پاساژ
- امتیاز/نظر کاربران
- صف، پارکینگ، دسترسی
- تأیید هویت فروشنده

هر کدام از این‌ها یا باید «صادقانه غایب» باشند یا با یک مکانیزم جایگزین (تأیید فروشنده، گزارش کاربر، آدرس متنی) پوشش داده شوند.

## ۴. بارم‌بندی و استراتژی امتیاز

| معیار | امتیاز | یعنی چه | کارهای برنده |
|---|---|---|---|
| محصول | ۷۵ | آیا واقعاً مشکل خرید حضوری را حل می‌کند و همه‌ی موارد خواسته‌شده را دارد؟ | پوشش کامل ۶ گام + اقساط + جایگزین + پاساژ |
| UX و تجربه کاربری | ۷۵ | آیا کاربر راحت و بدون دردسر کار می‌کند؟ | mobile-first، RTL، کارت/فیلتر به‌جای چت محض، شفافیت |
| هوشمندی | ۵۰ | پیگیری فروشنده، جایگزینیابی، توجه به شرایط مراجعه | حلقه‌ی تأیید، تایم‌اوت، مسابقه‌ی تأیید، مسیر سفر |
| دیپلوی | ۴۰ | کیفیت و پایداری انتشار | URL زنده، seed، healthcheck، CI، fallback |
| پیاده‌سازی فنی | ۴۰ | ساختار کد، ابزار درست، عملکرد، مقیاس | معماری تمیز، تست، eval، observability |
| دیتاست | ۲۰ | استفاده‌ی درست و نمایش شفاف | استفاده از هر سه جدول + semantics قیمت/موجودی |

**نتیجه:** ۲۰۰ امتیاز از ۳۰۰ مربوط به محصول، UX و هوشمندی است. معماری باید در خدمت دمو باشد، نه برعکس.

### ۴.۱ نقشه‌ی «هر امتیاز کجا دیده می‌شود»

- **محصول (۷۵):** دموی کامل از «نمی‌دانم چه کتونی» تا «رسیدن به مغازه».
- **UX (۷۵):** سه اسکرین موبایل تمیز، اسکلتون، میکرواینتراکشن، فیلترهای لمسی، متن فارسی روان.
- **هوشمندي (۵۰):** صحنه‌ی «فروشنده جواب نداد → جایگزین» و «قیمت عوض شد → هشدار».
- **دیپلوی (۴۰):** لینک باز در دمو + صفحه‌ی سلامت + داده‌ی seed.
- **فنی (۴۰):** ساختار پوشه‌ها، تست‌ها، eval، لاگ trace، جداسازی لایه‌ها.
- **دیتاست (۲۰):** نشان‌های تازگی/منبع + مقایسه‌ی قیمت با توزیع بازار + شفافیت پوشش.

## ۵. ریسک‌ها و پاسخ‌ها

| ریسک | احتمال | اثر | پاسخ |
|---|---|---|---|
| شماره‌های جعلی → عدم امکان تماس واقعی | قطعی | بالا | صندوق فروشنده + کانال شبیه‌سازی‌شده + شفاف‌سازی در دمو |
| کیفیت جست‌وجوی فارسی | متوسط | بالا | نرمال‌سازی + مترادف + FTS + بازرتبه‌بندی LLM |
| وابستگی به LLM و کندی/قطعی | متوسط | بالا | معماری state machine + fallback قاعده‌محور + mock provider |
| تحریم و عدم دسترسی LLM از سرور ایران | بالا | بالا | provider سازگار با OpenAI از طریق درگاه ایرانی/پروکسی |
| پوشش جغرافیایی ناقص دیتاست | قطعی | متوسط | نمایش شفاف پوشش + پیشنهاد نزدیک‌ترین منطقه‌ی موجود |
| نقشه‌ی داخل پاساژ وجود ندارد | قطعی | متوسط | آدرس متنی دقیق + جمله‌ی پرسیدن از نگهبان |
| دموی زنده خراب شود | متوسط | بالا | seed deterministic + کش + ویدئوی پشتیبان |
| زمان کم | بالا | بالا | فازبندی و اولویت‌بندی فیچرها |

## ۶. آنچه هنوز نمی‌دانیم

1. **نام دقیق ستون‌ها و enumها** (تا CSV را نبینیم، نمی‌توانیم ETL قطعی بنویسیم).
2. **ویدئوی چهار گام و پین‌پوینت‌ها** که در بریف به آن ارجاع شده و در PDF نیست.
3. **مناطق انتخاب‌شده‌ی تهران** در دیتاست (برای انتخاب لوکیشن پیش‌فرض دمو).
4. **دسترسی به LLM** و اینکه از سرور ایران قابل استفاده باشد یا نه.
5. **مقصد دیپلوی** و دسترسی حساب لیارا.

جزئیات درخواست‌ها در `docs/03-info-needed.md` آمده است.
