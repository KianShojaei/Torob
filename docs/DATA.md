# Data notes — what the dataset really is, and what we do about it

The challenge ships three CSVs (`shops`, `products`, `offers`). They are **not** a clean product
catalogue: they are a snapshot of listings with missing, stale and contradictory values. Everything
in Torbgard is designed around that fact.

---

## 1. Profile of the real snapshot

| Table | Rows | What is actually in it |
|---|---:|---|
| `shops` | 6,476 | 4,473 have opening hours, only 266 have `payment_options`; 19 malls, 30 neighbourhoods |
| `products` | 225,903 | 3,428 distinct category strings; `brand_name` is null for **74.5 %**; specs are free-text JSON |
| `offers` | 331,506 | 20,315 duplicate `(shop, product)` pairs; **15,083 null prices**; prices range from 0 to 10¹⁷ |

Consequences that drive the design:

* **A price is a claim with a date.** `last_price_changed_at` tells you when the seller last touched
  it — not whether the item exists on the shelf.
* **`category_names` is shop-level.** It says what a shop *tends to* sell, never that a specific
  offer is in stock.
* **Hours are partially known.** `unsupported` and missing days mean *unknown*, not *closed*.
* **`0/0` payment limits mean "no information".** Treating them as "no limit" would invent
  installment plans for products nobody will finance.
* **Names are demo values.** External lookups would fabricate facts, so we never do them.

The demo dataset generated by `app/etl/synthetic.py` reproduces these rates deliberately
(50,558 raw offers, 6 % duplicates, 4.5 % null prices, 31 % shops without hours, 19 malls).

## 2. Pipeline

```
CSV ──► readers ──► clean/normalise ──► derive ──► aggregate ──► SQLite + FTS5
        (BOM, delimiter, headers,        (hours, address,   (price stats,     (prebuilt at
         zip, null tokens, JSON)          price age,         mall clusters,    image build)
                                          installment)       shop stats)
```

`python -m app.etl.build --data ../data --db var/app.db` runs every stage in one pass and writes
`backend/var/etl-report.json`. Measured on this machine:

| Dataset | Shops | Products | Offers | Build time | DB size |
|---|---:|---:|---:|---:|---:|
| demo (`make synthetic`) | 1,200 | 30,000 | 47,652 | ~11 s | 67 MB |
| full scale (synthetic replica of §3) | 6,476 | 225,903 | 265,204 | ~74 s | 464 MB after `VACUUM` |

The build ends with `VACUUM`, so the file is dense and pages in quickly on a small container.

### Decisions, one by one

| Problem in the data | Rule applied | Where |
|---|---|---|
| `"null"` strings, empty cells, `nan`, `\N` | → `None`, never the literal | `etl/readers.py` |
| Malformed JSON in `specs`, `weekly_hours`, `contacts` | → `None` + counter, the row survives | `etl/readers.py` |
| Duplicate `(shop, product)` offers | keep the newest `last_price_changed_at` | `etl/build.py` |
| Price `0`, `< 10,000`, `> 5,000,000,000`, null | kept as a row but `price_valid = 0`; excluded from stats | `services/pricing.py` |
| Price age | bucket: `fresh` <7 d · `recent` ≤30 d · `old` ≤90 d · `stale` >90 d | `services/pricing.py` |
| Hours `unsupported` / missing | `unknown` → the UI says «نامشخص», never «بسته» | `services/hours.py` |
| Cross-midnight shift (`22:00–02:00`) | interval split across days, Tehran timezone | `services/hours.py` |
| Day keys `sat` / `saturday` / `شنبه` / `0` | all normalised to one canonical week | `services/hours.py` |
| Address with mall / floor / unit / landmark | parsed into parts + `addr_confidence` | `services/address.py` |
| Payment option with `channel != in_person` | counted as *declared*, not *confirmed* | `etl/build.py` |
| `0/0` installment limits | ignored for feasibility, kept as text | `services/pricing.py` |
| Category strings (3,428 variants) | mapped to 17 canonical categories, unknown kept verbatim | `etl/taxonomy.py` |
| Missing brand (74.5 %) | `NULL`, never inferred from the title | `etl/enrich.py` |
| Same product re-listed with a different title | conservative group key (brand + model + normalised title) | `etl/enrich.py` |

### Installment evidence

`has_in_person_installment = 1` only when a payment option exists **and** its `channel` is
`in_person`. The UI distinguishes three states:

| State | Persian | Meaning |
|---|---|---|
| confirmed | «قسطی تأییدشده» | a provider offers installments in this shop |
| declared | «قسطی اعلام‌شده» | payment data exists, channel unverified |
| none | «قسطی نامشخص» | no data — not "no installments" |

The strict filter (`installment=confirmed`) is a **hard** filter: shops without evidence are removed,
and the filter sheet says so.

## 3. Serving schema

```sql
shops(id, name, address, lat, lon, location_label, category_names, contacts, instagram,
      website_url, payment_options, has_in_person_installment, has_any_installment,
      installment_providers, supports_fast_delivery, weekly_hours, hours_known,
      mall_name, mall_key, floor, unit, unit_kind, landmark, street, addr_confidence,
      has_offers, offer_count, min_price, max_price)

products(id, title, title_folded, brand, category, model, image_urls, specs, key_specs,
         group_id, family, offer_count, shop_count, price_min, price_median, price_max,
         price_p25, price_p75)

offers(id, shop_id, product_id, price, price_valid, last_changed_at, age_days, age_bucket,
       seller_title, seller_title_folded, warranty, warranty_months)

malls(key, name, lat, lon, shop_count, categories, neighborhood)
negibourhoods(name, lat, lon, shop_count)
products_fts(product_id, title, brand, category, specs_text)  -- FTS5, unicode61 + custom folding
```

Indices cover `offers(product_id, price_valid)`, `shops(lat, lon)`, `products(category)`,
`products(brand)`, and the FTS table. Search uses bm25 with a synonym layer (کتونی → کفش ورزشی …).

### Postgres

The schema is plain SQL; `db/schema.py` is dialect-aware and the query layer uses no SQLite-only
feature except FTS. For Postgres: replace the FTS table with
`tsvector GENERATED ALWAYS AS (to_tsvector('simple', title || ' ' || brand))` + GIN index and swap
`bm25()` for `ts_rank`. Everything else (geo, hours, pricing) is pure Python.

## 4. Validation

`python -m app.etl.validate --db var/app.db` fails the build on:

* duplicate `(shop, product)` offers
* more than 300 offers for one shop
* a product without any offer row
* less than 90 % of products having a usable price
* coordinates outside the Tehran bounding box (> 2 % of shops)
* hours parsed for zero shops; no installment evidence at all
* in-person installment count exceeding total installment count
* unusable price rate outside 80–100 %
* FTS row count ≠ product count

It writes `backend/var/etl-validation.json`, which the demo report uses to quote real numbers.

## 5. Known limitations

* The in-mall guide is only as good as the address string; when the mall is unknown the UI shows a
  lower confidence and an **ask sentence** the user can paste into the chat.
* Product grouping is deliberately conservative — some duplicates stay separate rather than merging
  different models.
* Distances are haversine; there is no route-aware ETA without a routing key (documented in the UI).
* The synthetic dataset is statistically similar but **not** the real distribution; the UI always
  labels it «داده‌ی نمایشی».
