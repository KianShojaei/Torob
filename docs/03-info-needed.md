# اطلاعات و دسترسی‌های لازم برای شروع پیاده‌سازی

> هر مورد با **P0 / P1 / P2** علامت‌گذاری شده است.
> P0 = بدون آن نمی‌توان معماری نهایی و ETL را قطعی کرد. P1 = برای تجربه‌ی کامل لازم است. P2 = بهبود کیفیت.

---

## ۰. خلاصه‌ی خواسته‌ها در سه خط

1. **فایل دیتاست** (سه CSV: `shops`، `products`، `offers`) — از طریق GitHub یا پیوست چت.
2. **ویدئوی چهار گام چالش** یا لینک/متن آن (در PDF ارجاع داده شده ولی موجود نیست).
3. **تصمیم‌های زیرساختی**: provider مدل زبانی، حساب لیارا، کلید نقشه.

---

## ۱. P0 — بدون این‌ها شروع جدی ممکن نیست

### ۱.۱ دیتاست ⛔

**مشکل:** آدرس `startech.s3.ir-central1.arvanstorage.ir` از محیط توسعه‌ی من قابل دسترسی نیست (خطای SSL/اتصال). فقط `github.com`، `npmjs.org` و `pypi.org` باز است.

**راه‌های تحویل (به ترتیب ترجیح):**

| روش | مناسب برای | توضیح |
|---|---|---|
| **آپلود در یک ریپوی GitHub** | فایل بزرگ | می‌توانید ریپوی خصوصی بسازید و دسترسی بدید؛ من clone می‌کنم |
| **پیوست مستقیم در چت** | تا ~۲۵ مگابایت | اگر zip بزرگ است، به سه فایل تقسیم کنید |
| **فقط سرستون‌ها + ۲۰۰ ردیف نمونه از هر جدول** | شروع فوری | برای طراحی ETL کافی است؛ فایل کامل بعداً |

اگر هیچ‌کدام ممکن نیست، یک فایل `schema.txt` شامل:
- نام دقیق فایل‌ها و ستون‌ها
- ۳ نمونه ردیف از هر جدول (با داده‌ی واقعی)
- نوع داده‌ی هر ستون (عدد، متن، تاریخ، JSON)
- لیست مقادیر ممکن برای فیلدهای دسته‌ای (مثل نوع کسب‌وکار، وضعیت اقساط)

**چرا مهم است:** بدون دیدن ستون‌های واقعی، هر ETL و مدل داده‌ای که بنویسم حدس است و بعداً بازنویسی می‌خواهد.

### ۱.۲ ویدئوی چالش ⛔

در PDF نوشته شده «چهار گام دستیار در ویدئو توضیح داده شده است» و «چند نمونه از pain pointها در ویدئو توضیح داده شده». این ویدئو در فایل ارسالی نیست.

**لازم است:** لینک ویدئو، فایل ویدئو، یا حتی متن/اسکرین‌شات چهار گام.

اگر در دسترس نیست، بر اساس تحلیل PDF جلو می‌روم؛ اما ممکن است جزئیاتی از معیار داوری را از دست بدهیم.

### ۱.۳ تصمیم مدل زبانی ⛔

**محدودیت دوطرفه:**
- از سرور ایران، بسیاری از APIهای خارجی (OpenAI/Google) در دسترس یا مجاز نیستند.
- از این محیط توسعه هم فقط GitHub/npm/PyPI باز است؛ یعنی من نمی‌توانم کلید شما را همین‌جا تست کنم.

**گزینه‌ها:**

| گزینه | مزیت | نیاز |
|---|---|---|
| درگاه ایرانی سازگار با OpenAI (AvalAI، GapGPT، Metis، …) | از لیارا کار می‌کند | کلید + نام مدل |
| OpenRouter / پروکسی شخصی | تنوع مدل | پروکسی پایدار |
| Liara AI (اگر سرویس LLM دارد) | هم‌محل دیپلوی | بررسی مستندات |
| حالت mock + قاعده‌محور | بدون هزینه، پایدار برای دمو | هیچ |

**پیشنهاد من:** لایه‌ی `LLMProvider` با پیاده‌سازی‌های `mock`، `openai-compatible` و `rule-based`. در توسعه با mock کار می‌کنیم؛ کلید واقعی فقط در محیط لیارا ست می‌شود. **کلید را در چت نفرستید**؛ در `.env` لیارا قرار دهید.

### ۱.۴ مقصد و دسترسی دیپلوی ⛔

- حساب لیارا دارید؟ (اگر نه، باید بسازیم)
- نام اپ و منطقه‌ی مورد نظر؟
- دیپلوی از GitHub Actions انجام شود یا دستی؟

**نکته‌ی مهم:** من از این محیط نمی‌توانم به لیارا وصل شوم. دو مسیر:
1. **GitHub Actions** با سکرت `LIARA_API_TOKEN` (شما سکرت را در تنظیمات ریپو اضافه می‌کنید؛ من فقط workflow را می‌نویسم).
2. **اجرای دستی** دستورات توسط شما (من `Dockerfile` و `liara.json` را آماده می‌کنم).

### ۱.۵ زمان و تیم ⛔

- مهلت نهایی ارسال چه زمانی است؟
- چند ساعت در روز وقت دارید؟
- تنها کار می‌کنید یا تیم؟ (برای تقسیم کار و انتخاب عمق فیچرها)

## ۲. P1 — برای تجربه‌ی کامل

### ۲.۱ نقشه و موقعیت

| مورد | چرا لازم است |
|---|---|
| کلید **نشان** یا **مپ.آی‌آر** | تایل نقشه و مسیریابی از داخل ایران پایدارتر است |
| محله‌ی پیش‌فرض دمو | «ونک»، «سعادت‌آباد»، «نارمک»؟ باید از مناطق موجود در دیتاست انتخاب شود |
| آیا موقعیت واقعی کاربر (GPS) را می‌خواهید یا انتخاب دستی محله؟ | GPS در دمو ممکن است کند/مسدود باشد |

**پیشنهاد:** انتخاب محله به‌صورت دستی + دکمه‌ی «موقعیت من». برای دمو، یک محله‌ی ثابت که بیشترین فروشگاه را دارد.

### ۲.۲ کانال ارتباط با فروشنده

- آیا ربات **بله** دارید؟ (توکن)
- آیا WhatsApp Cloud API یا شماره‌ی واتساپ دارید؟
- آیا با مدل **صندوق فروشنده** (لینک اختصاصی + پاسخ وب) موافقید؟

**پیشنهاد:** صندوق فروشنده به‌عنوان کانال اصلی + لینک `wa.me` به‌عنوان کانال ثانویه + شبیه‌ساز برای دمو.

### ۲.۳ جست‌وجوی وب (بند «نتایج گوگل» در بریف)

بریف می‌گوید از نتایج جست‌وجوی گوگل استفاده کنید. برای این کار یکی لازم است:
- Google Programmable Search (کلید + CX)
- SerpAPI / Tavily / Brave Search
- یا **حذف این قابلیت** و اتکا به صندوق فروشنده

**پیشنهاد:** نسخه‌ی اول فقط صندوق فروشنده؛ اگر کلید Search داشتید، برای ۱۱۲ فروشگاه دارای سایت/اینستاگرام فعال می‌کنیم.

### ۲.۴ سیاست نمایش نام فروشگاه‌ها

۹۸٪ نام‌ها جعلی‌اند. سه راه:

| گزینه | توضیح |
|---|---|
| **الف) نمایش نام + برچسب «نام نمایشی»** | صادقانه، ولی ظاهر دمو کمی فنی می‌شود |
| **ب) نام مشتق‌شده از دسته + محله** | مثل «فروشگاه کفش — پاساژ آلتون»؛ صادقانه و خواناتر |
| ج) نمایش نام بدون توضیح | ریسک بدفهمی و ضعف در شفافیت (۲۰ امتیاز دیتاست) |

**پیشنهاد من: گزینه ب برای فروشگاه‌های جعلی، نام واقعی برای ۱۱۲ فروشگاه.** در تنظیمات یک سوییچ برای داوری بگذاریم.

### ۲.۵ برند و ظاهر

- نام محصول همان **ترب‌گرد** بماند یا پیشنهاد دیگری می‌خواهید؟
- رنگ اصلی؟ (پیشنهاد: سبز-آبی آرام + لهجه‌ی نارنجی برای CTA)
- لوگو بسازم یا خودتان دارید؟

## ۳. P2 — بهبود کیفیت

- دامنه/ساب‌دامین برای دیپلوی
- دسترسی به آنالیتیکس (یا رویداد داخلی)
- متن مجوز/شرایط استفاده
- آیا داده‌ی تصاویر محصولات از CDN ترب در دسترس است؟ (CORS/hotlink)
- ترجیح فونت: وزیرمتن یا ایران‌سنس؟

## ۴. پیش‌فرض‌هایی که اگر جواب ندهید انتخاب می‌کنم

| موضوع | پیش‌فرض |
|---|---|
| پشته | Next.js 15 + TypeScript + Tailwind + PostgreSQL روی لیارا |
| مدل | لایه‌ی تعویض‌پذیر؛ mock در توسعه، درگاه OpenAI-compatible در تولید |
| کانال تأیید | صندوق فروشنده + شبیه‌ساز |
| نقشه | Leaflet/MapLibre با تایل OSM؛ در صورت کلید نشان، سوییچ می‌شود |
| نمایش نام | نام مشتق‌شده + برچسب برای فروشگاه‌های بدون هویت واقعی |
| محله‌ی دمو | پرتراکم‌ترین محله‌ی دیتاست (بعد از پروفایل مشخص می‌شود) |
| زبان | فقط فارسی، RTL |
| ویدئو | ۵ دقیقه، اسکریپت در سند معماری |

---

## ۵. چیزهایی که می‌توانم همین حالا شروع کنم

بدون هیچ ورودی جدیدی:

- اسکلت پروژه با ساختار ماژولار
- سیستم طراحی RTL و کامپوننت‌های پایه
- اسکیمای دیتابیس و اسکریپت ETL (با ستون‌های حدسی، قابل تنظیم)
- داده‌ی نمونه‌ی مصنوعی برای ساختن UI
- ماشین حالت ایجنت و ابزارها با mock
- Dockerfile و workflow دیپلوی

بگویید «شروع کن» تا فاز ۰ و ۱ را روی همین برنچ بزنم.
